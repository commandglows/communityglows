# Gate retry leaves the parent access lock unchanged

## Reproduction and expected behavior

After an initial access-service outage, the app displays ProductAccessGate.
Once the backend recovers, clicking Vérifier à nouveau should update the parent
app's verified access and open the protected workspace.

## Diagnosis and observed behavior

App.vue and ProductAccessGate.vue each call useBillingAccess. Each call previously
created independent refs and an independent authentication watcher. A successful
gate refresh therefore left the parent's failed verification untouched. The gate
could lose its error message while the parent continued displaying the lock.

## Fix attempts

2026-09-08T22:00Z: Reproduced before repair using two Vue effect scopes. The gate
received active lifetime access after retry but the app's canAccessProtected was
false. A second test observed two initial backend requests instead of one.

Wrapped the existing factory in VueUse createSharedComposable. App and gate now
observe the same state while their scopes remain mounted. Existing sign-out reset,
server authorization, bounded outage grace, and Stripe opener changes are preserved.
VueUse disposes the shared watcher when the final consumer leaves.

2026-09-08T22:03Z: Hardened access refresh against late responses from a previous
authentication state or an older retry. A monotonically increasing request version
is invalidated synchronously by auth changes and final scope disposal. Only the
current request may publish access, errors or loading completion.

## Retest history

2026-09-08T22:00Z: Both new tests failed before repair and pass after repair.
`corepack pnpm exec vitest run src/composables/useBillingAccess.shared.test.ts src/composables/useBillingAccess.test.ts`
passes 35 tests. Regression coverage verifies retry updates the parent, gate
unmount retains app access, sign-out clears both consumers, final unmount removes
the auth subscription, and remount after an outage cannot reuse previous access.
Late successful responses after sign-out/sign-in or a newer denial cannot restore
old access. Additional checkout tests verify the native browser opener only receives
trusted Stripe URLs and browser popup blocking creates no checkout request.

Status: fixed-pending-verify. Automated state proof does not establish Windows
rendered acceptance. The root bug owner retains build, installation and native
protected-workspace verification. No production mutation or commit in this phase.
