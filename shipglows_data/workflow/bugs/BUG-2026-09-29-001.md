# Bug Record: BUG-2026-09-29-001

## Summary

The Windows candidate shows an entitlement-service failure before the user deliberately signs in. The screenshot proves the rendered failure, but does not prove an anonymous session: the application can restore an existing authenticated session. The gate promises account, export, privacy and sign-out recovery but renders no controls for those paths.

## Reproduction

- User opened the candidate Windows application and reported not having connected during this launch.
- Displayed screen: “Accès impossible à vérifier”, lifetime-purchase action, retry, support, red access-check failure.
- Exact persisted session and native route are unknown; do not infer absent tokens from the user's lack of a new sign-in.

## Expected Behavior

- An initial signed-out/loading session cannot show an entitlement failure or mount protected work.
- A restored-session access failure remains fail-closed and exposes working reconnect, billing recovery, export and privacy controls.
- A locked session renders unlock/sign-out recovery before any entitlement gate or protected workspace.

## Observed Behavior

- User screenshot contains the entitlement failure with no visible sign-in, reconnect, sign-out, export or privacy controls.
- Source: App.vue replaces the router/layout with ProductAccessGate whenever authenticated and access false; authenticated /login navigations redirect to /twitter.
- Root production diagnostic owner reports successful auth/users reads followed by billing:getProductAccess failing with bridge_not_configured. This separate runtime issue must be repaired without granting access or masking the failure as signed-out.
- Root localized the service failure to the next hop: CommandGlows Convex reported `bridge_secret_mismatch`. Vercel Production's existing `SUITE_BRIDGE_CONVEX_SECRET` was aligned with the unchanged canonical Doppler `commandglows/prd` and Convex `elegant-mule-677` value. No secret rotation or entitlement grant.
- After that deployment was READY, actual calls at 10:32:35 UTC still failed with the mismatch. At that point the hosted cause remained unresolved and root continued diagnosis. READY alone is not an access-service success.
- Later root read-only runtime inspection established that the secret actually evaluated by `elegant-mule-677` differed from the canonical Doppler value, while the CLI stored environment read matched Doppler. Reapplying the unchanged canonical value made the evaluated runtime value match. The reason for this stored/evaluated divergence is unknown; no platform defect is inferred.
- A read-only public bridge query then reached `global_user_not_found` for a deliberately nonexistent diagnostic identity, rather than `bridge_secret_mismatch`. This proves the secret boundary accepted the existing credential after reapplication; it does not prove a real customer's entitlement, the complete Windows billing flow, or any grant. No account/entitlement data was written.
- Stronger subsequent real-app evidence: CommandGlows `bridge:ensureCommunityGlowsEntitlementSnapshotByProviderAccount` completed without error at **10:50:19.551 UTC**, followed by CommunityGlows `billing:getProductAccess` completing without error at **10:50:19.640 UTC**. The same function pair previously failed at 10:41:16 UTC with mismatch/not-configured errors. Root observed these actual application calls without injecting identity, submitting authentication or fabricating a production action. The returned payload was suppressed, so the exact right/state and current Windows screen are not proven.
